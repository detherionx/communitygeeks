## 3. Chosen architecture: Eleventy (11ty), static output

**Why Eleventy:** the production constraint is hard — Communitygeeks is hosted on Hetzner legacy static webhosting, so the live site must be plain HTML/CSS/JS with no persistent Node server. Eleventy's whole model is "build static files locally/in CI, deploy the output folder" — it needs Node only at build time, never in production. It also stays close to the plain HTML/CSS this site was originally designed in, so the translation from approved mockup to templates was close to 1:1, minimizing the chance of introducing new bugs or drifting from what was approved.

Other options considered and rejected: Astro (more capable, but more opinionated/heavier than this project needs — five mostly-static pages don't need component islands or a JS framework runtime); a plain hand-written HTML site with no build step (would work, but loses the content-collection pattern for Public Thinking, meaning every new piece would require manually duplicating card markup in two places — this is explicitly what Section 6 of the original brief asked to avoid).

**No database, no CMS, no server-side runtime.** Content is Markdown files with frontmatter. This is deliberate, not a shortcut — the brief was explicit about this constraint and there's no concrete requirement here that needs more than that.

## 7. Content architecture: Public Thinking

This is the part of the brief most worth understanding properly before touching it.

**Why content/ lives outside src/:** so a non-technical editor (Katharina or Gaza) has exactly one folder to look in when adding a new piece, with zero risk of accidentally touching a template. The tradeoff: Eleventy's collections API only sees files inside the configured input directory (`src`), so `content/public-thinking/*.md` is invisible to `collectionApi.getFilteredByGlob()` — **I initially built this wrong, assuming glob-filtering worked across the whole project; it doesn't, and the build silently produced zero item pages with no error.** The actual fix: `src/_data/publicThinking.js` is a global data file that reads `content/public-thinking/*.md` directly via Node's `fs`, parses frontmatter with `gray-matter`, and renders the Markdown body with `markdown-it`. This is a normal, documented Eleventy pattern for content outside the input directory — not a hack — but it's worth understanding, because if you ever "simplify" this back to a plain `addCollection` + `getFilteredByGlob`, it will silently break again exactly the way it did for me.

**How to add a new piece:** copy `content/public-thinking/TEMPLATE.md.example` to a new file in the same directory (real filename, ending in `.md`, not `.md.example`), fill in the frontmatter, write the body in Markdown. It will automatically appear on `/public-thinking/`, get its own page at `/public-thinking/{slug}/`, appear in the sitemap, and — if it's one of the two newest pieces by date — on Home's preview grid. No template code needs to change.

**The confidence-label safeguard is real and tested**, not just a comment: `src/_data/publicThinking.js` throws a build-breaking error if any content file's `confidence` field isn't exactly `"Observation"`, `"Emerging Pattern"`, or `"Research Finding"` — these are the only public-facing labels approved in the Public Source Pack. Internal OS labels (Low/Medium/High/Validated, or Weak/Emerging/Strong) must never reach this repo. I deliberately broke this during verification (set an invalid value, confirmed the build failed with a clear message, then reverted) — see the build log if you want proof this actually works before trusting it.

**CMS decision (2026-08-11): holding off on Decap CMS for now.** It came up as a "still open" item, but adding it means standing up an OAuth backend to authenticate editors against GitHub (Netlify Identity, or a self-hosted proxy) — real new infrastructure that cuts against the whole static-site-on-Hetzner rationale in Section 3. With only two placeholder pieces and low expected publishing cadence, the existing copy-template-and-commit workflow is simple enough. Revisit once there are a few real published pieces, or if a non-technical editor needs to publish without going through Git at all.

**The two existing content files are not real yet.** `community-devrel-partnerships-overlap.md` and `moat-or-funnel-diagnostic.md` were introduced as illustrative card copy during the design phase — plausible titles that mirror real research directions in the OS, but never checked against an actual finished writeup. Their bodies currently say exactly that, explicitly, in an HTML comment and in the visible body text. **Do not write real-sounding analysis into these files yourself** — that would be fabricating research findings, which the original brief explicitly prohibited. Wait for Carmelito or Katharina to supply real content, or ask.

## 11. Fixed bug (2026-08-11): missing media-query closing brace

`src/assets/css/style.css` had a missing `}` after the `.pt-grid{grid-template-columns:1fr;}` line inside `@media (max-width:860px){...}`. Everything from the "Shared page-header pattern" comment through the end of the file — all of About, Approach, Contact, and the Public Thinking index page's actual styling (`.index-card`, `.index-grid`, `.filter-bar`, `.filter-pill`, `.card-title`, `.form-mock`, `.contact-grid`, `.principle-list`, `.approach-detail`, etc.) — was accidentally nested inside that mobile-only media query, so none of it applied at normal desktop widths. ## 12. Fixed bug (2026-08-11): no mobile nav, and two more un-collapsed grids

Two separate mobile-layout problems, found by actually testing at a 375px viewport (not just visual inspection):

1. **The nav bar never had a mobile version at all.** `.navlinks` + `.nav-cta` were plain desktop flex children of `nav` with no collapse behavior — at narrow widths they simply overflowed instead of wrapping, pushing "About" and "Compare notes" off-screen entirely (present but unreachable without horizontal scrolling — this is what looked like "menu links do nothing"). Fixed by adding a real hamburger: `nav.njk` now wraps `.navlinks` + `.nav-cta` in `#nav-menu`, with a `.nav-toggle` button before it; `src/assets/js/nav-toggle.js` toggles a `.open` class + `aria-expanded`; CSS hides `.nav-toggle` and shows `.nav-menu` inline above 860px (the token breakpoint that already existed in `tokens.json` but was never actually wired to anything), and the reverse below it, as an absolutely-positioned dropdown.
2. **`.contact-grid` and `.approach-detail` never collapsed to one column** — no override existed for either, so at mobile widths the two-column grid (`0.85fr 1fr` / `80px 1fr`) squeezed the second column down to ~1px, which for Contact meant the Typeform embed rendered at effectively zero width.

**A cascade-order trap worth remembering**: my first attempt at fixing (2) added the overrides to the *first* `@media (max-width:860px)` block (the one near the top of the file, right after nav/hero). That block sits *before* `.contact-grid`'s and `.approach-detail`'s own base rules further down the file (CONTACT PAGE / APPROACH PAGE sections) — and since both rules have equal specificity, the *later* one in source order wins regardless of the media condition being true. The override was being correctly parsed and served, and still doing nothing, which looks exactly like a caching problem until you check rule order specifically. Fix: moved both overrides into the *second*, smaller `@media` block at the very end of the file, which comes after every page-specific section. **Any future mobile override for a selector defined in one of the later page-specific sections must go in that final media block, not the early shared one** — check where the base rule actually sits before adding an override, don't assume "inside any `@media` block" is sufficient.

Verified all of this with real computed-style / `document.documentElement.scrollWidth` checks at a 375px viewport (not just visual inspection) on every page: `/`, `/about/`, `/approach/`, `/contact/`, `/public-thinking/`, and a Public Thinking item page.

## 14. Logo badge + marquee (2026-08-11)

Replaced the first-pass client logos (plain `<img>`, wildly inconsistent native sizes/colors, flagged by Carmelito as broken) with a shared `.logo-badge` component used in two places: the "Trusted by industry leaders" marquee (`.trust` section, replacing the old plain-text trust strip entirely) and Selected Work's cards (`.logo-badge-sm`).

**How it works (revised same day — see Section 15 below)**: each badge is a fixed-size box (120×56 in the marquee, 96×40 in Selected Work) containing one layer, `.logo-mono` — the logo rendered via CSS `mask-image`, filled with `var(--ink-soft)`, so it shows as a flat silhouette *regardless of the source image's actual colors*. There is no color-reveal layer anymore (`.logo-color` was removed same day, see Section 15). The logo URL is passed once per instance via an inline `--logo-url` custom property, not duplicated in CSS.

**Why this solves the Space Whale / ZAM problem without touching their artwork**: both have white-only official marks (their sites are dark-background, no light variant exists). `mask-image` only cares about the source image's alpha channel/silhouette, not its actual painted color — so their white shapes work perfectly as a mask filled with our own ink color. Since there's no color-reveal state at all anymore, there's also no risk of their real white pixels ever vanishing against a light background — the silhouette is the only state, permanently.

**Data model**: `clients.json` gained a `logoWall` array (7 entries: DeepL, EU Academy [rendered via the European Commission logo], Tencent, ZAM, Space Whale, Billbee, GB Foods) feeding the marquee. `selectedWork` is unchanged in shape, just renders through `.logo-badge-sm` now instead of `.work-logo` (which no longer exists). ZAM was deliberately added only to `logoWall`, not as a second Selected Work card — Carmelito wanted both marks visible for brand recognition, but the founder's original naming decision (display "Tencent," not "ZAM," in the detailed case-story cards) still stands.

**Marquee mechanics**: `.marquee-track` holds the 7 real badges (each with a `.sr-only` accessible name) followed by an identical `aria-hidden="true"` duplicate set, animated via `transform:translateX` from `0` to `-50%` — since the content is duplicated, `-50%` is exactly where it seamlessly loops. Paused on hover (`animation-play-state:paused`) so a visitor can actually read/hover an individual logo instead of chasing a moving target. Respects `prefers-reduced-motion`.

**A debugging note worth keeping**: while verifying this, `:hover` and forced inline `!important` background changes appeared not to apply at all when checked via this environment's automated browser tool — even though the CSS was correct. Root cause: `.logo-badge` has `transition: background .2s`, and CSS transitions are driven by the same paint/compositor timeline that this specific tool's headless tab wasn't running ("Browser pane is not displayed" blocked every screenshot attempt too). Setting `transition:none !important` on the same element made the change apply instantly, confirming the CSS itself was correct and the failure was purely environmental. If a future session hits the same "my hover/transition style won't apply in the browser tool" symptom, check this before assuming the CSS is wrong.

## 15. Logo badge fixes, round 2: opaque source PNGs, real DeepL logo, dropped color-reveal (2026-08-11)

Same day as Section 14, once the marquee actually went live, three real problems surfaced:

1. **Billbee and GB Foods rendered as solid dark rectangles instead of their logo shape.** Root cause, confirmed by reading actual pixel alpha data (not just PNG format bytes — a file can declare an alpha channel and still have zero real transparency): `gb-foods.png` was **100% opaque** and `billbee.png` was **99.9% opaque** — both source files bundled a solid background tile into the export instead of isolating the mark on a transparent background. `mask-image` needs real transparency to know what shape to cut out; without it, it just paints the whole box. This was a source-asset problem, unrelated to the color-reveal mechanism — it would have broken either way. **Fixed** by removing each file's flat background color programmatically (sampling the dominant background color, zeroing alpha within a tolerance, feathering the edge) — this only touches the background, the actual logo artwork/colors are untouched. Also discovered along the way: the *original* `gb-foods.png` download was genuinely corrupt — not a real PNG at all, but a WebP file (`VP8X` chunk signature) mislabeled with a `.png` extension and `Content-Type: image/png` by thegbfoods.com's own CDN. Chrome's `<img>` tag silently content-sniffs and decodes it anyway (which is why it looked fine in casual checks), but a strict PNG parser (Node's `pngjs`) correctly rejected it. Re-downloading didn't help (byte-identical corruption from their server) — `sharp` decoded it correctly via format sniffing, same as Chrome, and re-exports a genuinely standards-compliant PNG. If GB Foods' logo ever needs updating again, verify the downloaded bytes are actually PNG (`buf.slice(0,8).toString('hex') === '89504e470d0a1a0a'`) before assuming a `.png` URL served it correctly.
2. **DeepL's logo was "incomplete."** What got sourced originally (Section 4/8) was DeepL's wordmark-only file. DeepL's press page actually has two separate current assets — wordmark and icon — both the same current blue (`#0F2B46`), never combined into one lockup file by DeepL themselves. Carmelito linked a Wikimedia file as a reference, but that's DeepL's *old 2017* logo (different proportions, dated) — using it would have meant shipping outdated branding. Fixed by combining DeepL's two *current* official assets into one lockup SVG (`src/assets/images/logos/deepl.svg`, icon scaled and positioned left of the wordmark via nested `<g transform>` groups, original path data untouched). **A real mistake made and fixed while building this**: an XML comment inside the combined SVG contained a literal `--` in the middle of the text ("assets together -- see HANDOFF.md"), which is invalid inside an XML/SVG comment (only allowed immediately before the closing `-->`) — this silently broke the `<img>` load entirely. Any future hand-written comment inside an SVG/XML file needs checking for stray `--` sequences.
3. **Dropped the color-reveal/dark-background-flip hover effect entirely**, per Carmelito's direct request — the boldcreators.club reference he pointed to keeps logos monochrome always and only does "some slight effect" on hover, not a color reveal. `.logo-color`, its cross-fade, and the `:hover` background flip to `var(--ink)` are gone from both the CSS and the templates. Hover is now just `border-color` → `var(--ink)` plus a 2px lift (`transform:translateY(-2px)`). This is also strictly safer going forward: there is no longer any state where a white-only mark (Space Whale, ZAM) needs a special dark background to stay visible — the silhouette is the only state that ever renders.

Verified end to end: re-checked actual pixel alpha for all 7 `logoWall` assets after the fixes (all now 56–96% transparent, vs. Billbee/GB Foods at ~0% before), confirmed zero `.logo-color` elements remain in the rendered HTML, and rasterized the combined DeepL SVG through `sharp` to a PNG to visually confirm it actually shows the icon + wordmark together before shipping.

**Round 3, same day: GB Foods rendered tiny relative to the other badges.** `mask-size:contain` scales against the *entire image canvas*, not the visible content — GB Foods' 1840×1476 canvas had enormous transparent padding around the actual ~1102×278 mark (an aspect ratio of 1.25:1 for the canvas vs. 3.96:1 for the real content), so the visible logo rendered far smaller than logos whose source files were already tightly cropped. Fixed with `sharp().trim()` (crops to the actual non-background bounding box — purely mechanical, no artwork altered) on `gb-foods.png` (1840×1476 → 1102×278) and `billbee.png` (280×112 → 205×42, less dramatic but real padding). Left `european-commission.svg`'s modest padding (291×72 → 258×67 trimmed) alone — trimming it would mean rasterizing a vector file for a small gain, not worth the tradeoff. **If any future logo looks disproportionately small or large in a badge, check `sharp('<file>').trim()`'s reported dimensions against the file's actual metadata dimensions before assuming it's a CSS problem** — a mismatch there is almost certainly the real cause, not `mask-size` or the badge CSS itself.

## 18. Marquee overflow on very wide viewports (2026-08-16)

The "Trusted by industry leaders" marquee's seamless-loop technique (duplicate the 7-logo set once, animate `translateX` from `0` to `-50%`) needs each half of the track to be at least as wide as the viewport, or the animation runs out of content mid-cycle and shows a visible gap before looping. With only 7 real clients, one set's width (~1000px) comfortably covers a normal laptop screen but not a large/ultrawide monitor (Carmelito hit this on his own screen; boldcreators.club, the reference for this component, has ~10 logos so didn't show the same problem at the same viewport width).

Fixed with `src/assets/js/marquee.js` (loaded only on the homepage via `extraScripts`): on load, measures the track's actual half-width against `window.innerWidth`, and if insufficient, clones the existing sets (all marked `aria-hidden="true"`) enough times to comfortably exceed the viewport, preserving the "two equal halves" invariant the CSS `-50%` loop depends on — so the loop point stays correct regardless of how many sets end up in each half. Also re-checks on window resize (debounced). Verified at 3440px viewport: half-width grew from 1022px to 5166px (70 total badges), while a normal-width viewport still renders exactly the original 14 with no unnecessary clones. Verified separately that only the original 7 real badges are ever exposed to screen readers — `aria-hidden="true"` on a cloned badge correctly excludes its `.sr-only` name from the accessibility tree regardless of how many raw `.sr-only` elements exist in the DOM, so the clone count growing large is not an accessibility regression.
